# 百度 Web 矢量瓦片

2026-10-23 完成独立前端验证原型，入口为
[百度矢量 GIS 验证页](../../tools/baidu-gis-prototype/README.md)。
当前不改变桌面程序的 GIS 来源；百度卫星和电子栅格底图此前已经接入。

## 来源与版本

- 官方 SDK：`https://api.map.baidu.com/getscript?v=1.0&type=webgl`。
  本轮 `TILE_VERSION.ditu.normal` 为版本 088、更新标记 20261021。
- 原生矢量请求来自 SDK `getTilesUrl`，使用
  `https://maponline0.bdimg.com/pvd/?qt=vtile&param=...`。
  `param` 内容为 `x/y/z`、`styles=pl`、`textimg=0`、版本及更新标记、`json=0`。
- 参数按 SDK `hq` 逻辑编码：ASCII 左移一位、串接八位表示、左侧填充至五位分组，
  每组加 50 后转字符，末尾附填充位数，再进行 URL 编码。
  直接传未编码参数的试验返回 404，不能由此认定矢量不存在。
- 官方 ASM 解码器来自 SDK 明确引用的
  `https://api.map.baidu.com/res/webgl/10/worker_asm_3u43mq.js`。
  本机只在无文件、网络能力的 VM 上下文中运行离线参考数学函数；
  SDK 和原始瓦片不提交到仓库。
- 这是 SDK 内部接口，不能当作稳定公开协议。缓存记录 SDK SHA-256，
  并按矢量版本和更新标记分目录。

## 格网与坐标

百度原生矢量的格网与普通 256 像素栅格不同。SDK 的
`mapZoomBaseZoomMapping`、`baseScaleZoomMercatorSize`、`baseScaleTileSize`
共同决定选块，不能只对百度栅格索引翻转 Y 或套用腾讯 XYZ。

| 原生数据层级 | 局部尺寸 | 百度墨卡托跨度 |
| --- | ---: | ---: |
| 3 | 256 | 8388608 |
| 5 | 512 | 4194304 |
| 7 | 512 | 1048576 |
| 9 | 512 | 262144 |
| 10 | 256 | 65536 |
| 12 | 512 | 32768 |
| 15 | 512 | 4096 |
| 17 | 1024 | 2048 |
| 19 | 1024 | 512 |

显示 z18 对应原生数据 z19，数据索引以表中跨度计算：
`x=floor(mcX/span)`、`y=floor(mcY/span)`，Y 向北增加。
北京 BD09 `116.425,39.886` 在原生 z19 下为 `25313,9417`，
已与百度网页实际请求对照。

面和线的 Int32 顶点分别累计 X/Y 差分，再除以 100 得到局部坐标；
转为百度墨卡托时乘 `span/localSize`，加上瓦片原点。
地点锚点的头字段使用局部墨卡托百分之一单位，按 SDK 四舍五入后加瓦片原点；
不能把地点头套用线面的差分缩放。

前端投影系数与现有 `BaiduDown` 一致，并用四城经纬度往返核对。
前端坐标保持 BD09；正式输出必须转换为 WGS84，不能只改 GeoJSON 标签。

## 二进制与几何

已验证格式的前两个 Uint32 为 `2,2`。顶层目录分为五段，
其中地表基础数据再按图层块、样式块、要素块组织。
目录记录子块长度，内容以四字节对齐；读取前检查目录、长度和索引边界。

已确认的原始几何组：

| 组编号 | 当前显示类别 | 参考入口 |
| --- | --- | --- |
| 3 | 地点 / 文字锚点 | SDK `mc` |
| 4 | 地表线 | SDK `xd` |
| 7 | 地表面 | SDK `Pc` |
| 8 | 建筑 | SDK `Qc` |
| 15 | 叠加面 | SDK `Pc` |
| 16 | 立体线 | SDK `xd` |

图层顺序和样式编号都保留原值。上述几何组不等于业务分类：
水体、绿地、道路、高速、边界、地铁的映射仍需独立核对。
官方自定义样式入口的无 AK 试验返回 `status=2`、`[ak]为必选参数`，
本轮没有使用其他人的 AK 或从样式颜色推断类别。

面使用服务返回的 Uint16 三角索引绘制。验证 GeoJSON 用 GeometryCollection
保留这些三角面，不将其冒充已恢复的 Polygon 外环和洞。
正式接入前，需要利用已有几何库核对三角网格到外环/洞的拓扑恢复方案。

建筑头第三值在 SDK 中直接传给 `_append_block_data`，
其数值与生成网格 Z 分量一致。本轮以 `heightRaw` 保留；
尚未核对完整渲染矩阵到米制高度的变换，不能写为 `heightMeters`。

## 对照结果

四城 × 原生 z12/z15/z17/z19，共 16 组，解析 36,320 个要素。
194,378 个顶点与 SDK `td` 的双精度结果一致。
官方 ASM `Zb` 逐次写入 Float32，已用相同的 Float32 累加单独核对；
与双精度的最大局部差异约为 0.002906，不是点序或比例错误。
692 栋建筑的高度原值与 ASM 挤出网格 Z 分量一致。

1440×900、390×844 检查真实地图像素、Canvas 非透明像素、类别选择、
要素点击、底图关闭及筛选 GeoJSON 主动下载；没有脚本错误和横向溢出。
北京九瓦片解析 4,496 个要素，包含 1,040 栋建筑。
验证数据和报告留在本机 `tmp/baidu-gis-research/` 供复查。

## 正式接入前

1. 补齐业务分类表，不能把所有地表线归为道路、所有地表面归为绿地。
2. 核对高度字段的物理单位及源瓦片内面拓扑，包含多环、洞和缓冲区。
3. 继续核对未解析的新几何组、道路文字、箭头、符号及室内数据；
   前端显示未解析图层编号和块数量，原始数据保留在缓存。
4. 完成后再增加百度专用 C++ 解码/下载模块、来源标识和版本化缓存，
   复用现有 WGS84 转换、范围处理及多格式导出后端。
5. 不能让前端验证页的 BD09 三角面输出直接进入正式 WGS84 建筑导出。
