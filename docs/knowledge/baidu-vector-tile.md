# 百度 Web 矢量瓦片

2026-10-23 完成独立前端验证原型，入口为
[百度矢量 GIS 验证页](../../tools/baidu-gis-prototype/README.md)。
当前不改变桌面程序的 GIS 来源；百度卫星和电子栅格底图此前已经接入。

## 来源与版本

- 官方 SDK：`https://api.map.baidu.com/getscript?v=1.0&type=webgl`。
  本轮 `TILE_VERSION.ditu.normal` 为版本 088、更新标记 20261021。
- 原生矢量请求来自 SDK `getTilesUrl`，使用
  `https://maponline0.bdimg.com/pvd/?qt=vtile&param=...`。
  `param` 内容为 `x/y/z`、`styles=pl`、`textimg=0`、版本及更新标记、`json=0`。
- 参数按 SDK `hq` 逻辑编码：ASCII 左移一位、串接八位表示、左侧填充至五位分组，
  每组加 50 后转字符，末尾附填充位数，再进行 URL 编码。
  直接传未编码参数的试验返回 404，不能由此认定矢量不存在。
- 官方 ASM 解码器来自 SDK 明确引用的
  `https://api.map.baidu.com/res/webgl/10/worker_asm_3u43mq.js`。
  本机只在无文件、网络能力的 VM 上下文中运行离线参考数学函数；
  SDK 和原始瓦片不提交到仓库。
- 这是 SDK 内部接口，不能当作稳定公开协议。缓存记录 SDK SHA-256，
  并按矢量版本和更新标记分目录。

## 格网与坐标

百度原生矢量的格网与普通 256 像素栅格不同。SDK 的
`mapZoomBaseZoomMapping`、`baseScaleZoomMercatorSize`、`baseScaleTileSize`
共同决定选块，不能只对百度栅格索引翻转 Y 或套用腾讯 XYZ。

| 原生数据层级 | 局部尺寸 | 百度墨卡托跨度 |
| --- | ---: | ---: |
| 3 | 256 | 8388608 |
| 5 | 512 | 4194304 |
| 7 | 512 | 1048576 |
| 9 | 512 | 262144 |
| 10 | 256 | 65536 |
| 12 | 512 | 32768 |
| 15 | 512 | 4096 |
| 17 | 1024 | 2048 |
| 19 | 1024 | 512 |

显示 z18 对应原生数据 z19，数据索引以表中跨度计算：
`x=floor(mcX/span)`、`y=floor(mcY/span)`，Y 向北增加。
北京 BD09 `116.425,39.886` 在原生 z19 下为 `25313,9417`，
已与百度网页实际请求对照。

面和线的 Int32 顶点分别累计 X/Y 差分，再除以 100 得到局部坐标；
转为百度墨卡托时乘 `span/localSize`，加上瓦片原点。
地点锚点的头字段使用局部墨卡托百分之一单位，按 SDK 四舍五入后加瓦片原点；
不能把地点头套用线面的差分缩放。

前端投影系数与现有 `BaiduDown` 一致，并用四城经纬度往返核对。
前端坐标保持 BD09；正式输出必须转换为 WGS84，不能只改 GeoJSON 标签。

## 二进制与几何

已验证格式的前两个 Uint32 为 `2,2`。顶层目录分为五段，
其中地表基础数据再按图层块、样式块、要素块组织。
目录记录子块长度，内容以四字节对齐；读取前检查目录、长度和索引边界。

已确认的原始几何组：

| 组编号 | 当前显示类别 | 参考入口 |
| --- | --- | --- |
| 3 | 地点 / 文字锚点 | SDK `mc` |
| 4 | 地表线 | SDK `xd` |
| 7 | 地表面 | SDK `Pc` |
| 8 | 建筑 | SDK `Qc` |
| 15 | 叠加面 | SDK `Pc` |
| 16 | 立体线 | SDK `xd` |

图层顺序和样式编号都保留原值。上述几何组不等于业务分类；
业务类型采用下面已确认的官方查询映射，不能从几何组或默认颜色推断。

面使用服务返回的 Uint16 三角索引绘制。验证 GeoJSON 用 GeometryCollection
保留这些三角面，不将其冒充已恢复的 Polygon 外环和洞。
正式接入前，需要利用已有几何库核对三角网格到外环/洞的拓扑恢复方案。

建筑头第三值在 SDK 中直接传给 `_append_block_data`，
其数值与生成网格 Z 分量一致。本轮以 `heightRaw` 保留；
尚未核对完整渲染矩阵到米制高度的变换，不能写为 `heightMeters`。

## 业务分类与登录

2026-10-23 继续核对官方个性化编辑器公开脚本
`https://lbsyun.baidu.com/customv2/main.8c8cbf6c91ead731fef2.bundle.js`：
`hotspotrightclick` 处理函数把要素 `styleIds` 交给
`https://api.map.baidu.com/custom/v2/getfeaturetype`，再用返回的类别字符串构建菜单。
公开脚本中的类别树给出了水系、绿地、教育区域、医疗区域及各类道路等名称。

实际请求使用 `feature_ids=编号列表&callback=baiduFeatureTypes`。
响应为 JSONP 包装的字符串数组，顺序与输入逐项对应；批量和单独查询已交叉核对。
只对固定包装做 JSON 解析，不执行返回脚本；长度不匹配、错误文本和非法类别明确报错。
本轮无登录、无 Cookie、无 AK 的直接请求成功，缺少 callback 时返回
`callback parameter error`，不能把该响应误判成需要登录。

| 原始编号示例 | 官方类别 | 验证页类别 |
| --- | --- | --- |
| 60001、60003、1506 | WATER | 水体 |
| 20902、61942、2534 | GREEN | 绿地 |
| 504316、504317、504319 | BUILDING | 建筑 |
| 60559、61197 | PROVINCIALWAY | 道路；保留省道原始类型 |
| 60604 | HIGHWAY | 高速 |
| 1803、501765 | RAILROAD、HIGHRAILWAY | 铁路 / 高铁 |
| 20003、20005 | SUBWAY | 地铁 |
| 1563、1603、2932 | EDUCATION、MEDICAL、SCENICSPOTS | 教育、医疗、景点区域 |
| 1604、1601、1549 | AOIOTHER | 其他人造区域 |
| 504812、504813 | 空字符串 | 道路；使用下述已核对的补充规则 |
| 505126 | 空字符串 | 未分类 |
| 501776 | UNCLASSIFIED | 未分类 |

保留 `featureType`、`resolvedFeatureType`、`geometryCategory`、`classificationKnown` 和
`classificationSource`。地点或文字锚点保留原始业务类型，但渲染/导出仍归点，
防止“水体名称”混入水体几何、“建筑名称”混入建筑面。
业务分类查询完成后才整体替换预览；失败或取消保留上次数据，
不会以缺失分类冒充成功。接口响应按矢量版本和更新标记分批缓存。

登录和 AK 是不同要求：旧 `/apiconsole/custommap/edit` 页面在未登录时跳转登录页，
此前尝试的 `/custom/v2/mapstyle` 返回 `[ak]为必选参数`。
这不适用于已经实测可用的 `getfeaturetype` 查询，也不代表下载默认矢量瓦片需要登录。
没有将官方页面内置 AK 复制到验证页或代理请求中。
这些均为内部接口，本轮结果不保证未来的认证策略或分类表不会改变。
高层级部分附加图层仍返回空类别；行政边界及未解析几何组需另行取样核对。

### 内部道路漏分类修正

百度能绘制道路不等于 `getfeaturetype` 覆盖了所有绘制编号。用户指出的停车场环路
位于原生 z19 的 `25314,9417`，组 15、编号 `504812`、101 个顶点及 93 个三角面。
接口对 `504812/504813` 返回空字符串，而默认 `fs.js` 对这两个编号有面绘制样式。
官方 ASM 的 `vd` 在道路绘制分支处理组 15，并通过 `Pc` 绘制道路面。
仅凭该分支或颜色仍不足以确定业务类型，还做了以下几何对照：

- 环路 93 个三角面中心的最近原生 z17 线全部是官方 `LOCAL`、编号 60499；
  百度墨卡托距离平均约 1.073、最大约 3.193。
- 北京、济南、上海、广州的同编号道路面，与已分类的内部道路、景区道路等中心线
  进行跨层级位置对照；`504813` 同样是道路面。一个编号可能包含不同道路等级，
  因此补充结果只写道路大类 `ROAD`，不把所有这些面强行标为 `LOCAL`。
- 规则严格限定矢量版本 088、更新标记 20261021、原生 z19、组 15 和两个明确编号；
  官方查询有明确类型时优先使用官方结果。其他编号、其他组、版本变化均不套用。
- `featureType` 继续保留接口原始空字符串，`resolvedFeatureType` 为 `ROAD`，
  `classificationSource` 为 `verified-road-surface`；界面筛选及导出均保留此来源。
  不能把补充规则描述成官方分类接口的返回值。

没有把所有 `UNCLASSIFIED` 合并为道路：例如 60924 的默认线样式带
`MapRes/lundu` 渡轮纹理，501776 则仍缺少精确类型。这些记录继续保留未分类。
默认样式来源为 SDK 引用的 `https://maponline0.bdimg.com/sty/fs.js`，
本轮样式标记为 `udt=20261013&v=001`；它与矢量版本标记分别记录。

## 对照结果

四城 × 原生 z12/z15/z17/z19，共 16 组，解析 36,320 个要素。
194,378 个顶点与 SDK `td` 的双精度结果一致。
官方 ASM `Zb` 逐次写入 Float32，已用相同的 Float32 累加单独核对；
与双精度的最大局部差异约为 0.002906，不是点序或比例错误。
692 栋建筑的高度原值与 ASM 挤出网格 Z 分量一致。

1440×900、390×844 检查真实地图像素、Canvas 非透明像素、类别选择、
要素点击、底图关闭及筛选 GeoJSON 主动下载；没有脚本错误和横向溢出。
北京九瓦片解析 4,496 个要素，包含 1,040 栋建筑。
验证数据和报告留在本机 `tmp/baidu-gis-research/` 供复查。

同一批四城 16 组样本含 374 个不同样式编号，分类查询返回 323 个非空类别。
非点要素中 33,209 个获得明确业务分类，1,298 个为空类型或 `UNCLASSIFIED`。
已确认水体 1,345 个、绿地 264 个、建筑 692 个、铁路/高铁 443 个、地铁 117 个。
原始类别、按样区/层级计数和未分类编号记录在本机 `classification-report.json`。
上述为官方查询原始结果；道路补充规则另外识别四城样本中的 271 个道路面，
以及北京九瓦片中的 330 个道路面。北京道路类别由 499 增至 829，
未分类由 2,004 降至 1,674；几何和瓦片数量不变。

## 正式接入前

1. 继续核对高层级未分类编号、行政边界和未解析几何组；
   已确认分类直接采用官方映射，不把所有地表线归为道路、所有地表面归为绿地。
2. 核对高度字段的物理单位及源瓦片内面拓扑，包含多环、洞和缓冲区。
3. 继续核对未解析的新几何组、道路文字、箭头、符号及室内数据；
   前端显示未解析图层编号和块数量，原始数据保留在缓存。
4. 完成后再增加百度专用 C++ 解码/下载模块、来源标识和版本化缓存，
   复用现有 WGS84 转换、范围处理及多格式导出后端。
5. 不能让前端验证页的 BD09 三角面输出直接进入正式 WGS84 建筑导出。
