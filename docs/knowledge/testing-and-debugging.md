# 测试与调试经验

## 导出任务取消必须贯穿整个流水线

### 现象

运行中的导出任务点击“取消”后界面看似没有反应，任务仍可能继续执行缓存扫描、
合并大图或 FBX 后处理，直到当前长阶段结束才显示“已取消”。

### 影响范围

卫星瓦片缓存扫描与下载、XYZ 金字塔、合并大图、FBX、GIS 下载与渲染、GIS 图像
复制与合成、GeoJSON 写出，以及任务进度 UI。

### 根因

- 任务管理器只向当前已注册的下载器设置停止标志，下载器注册前存在取消竞态。
- 多个 CPU 和文件处理长循环没有检查停止标志。
- 取消后的普通进度回调仍会覆盖“正在取消”状态。
- 原测试没有真正调用 `ExportTaskManager::Cancel()`，无法覆盖并发时序。

### 解决方案

- 下载器同时读取自身停止标志和任务管理器提供的取消回调。
- 所有长循环在领取下一项工作前检查取消，阶段边界再次检查。
- 文件复制、图像合成和 GeoJSON 写出接受同一个取消回调。
- 任务进入取消状态后忽略后续普通进度，界面禁用取消按钮并显示“正在取消”。
- 用可控下载器建立无网络回归测试，覆盖运行中、排队中和下载器注册前取消。

### 验证方式

- `ExportTaskManagerTest`：任务取消状态、最终状态和注册竞态。
- `PostProcessPyramidTest`：停止后不再领取下一张后处理瓦片。
- `AmapVectorGeoJsonTest`：取消时不创建 GeoJSON 输出。
- `AmapVectorPngTileTest` 与完整 CTest：检查 GIS 与其他导出行为没有回归。

### 快速检查清单

- 新增长阶段是否在内部循环和阶段边界都检查取消？
- 取消发生在资源注册前时，后续工作是否仍会启动？
- 取消后的进度回调是否会覆盖取消状态？
- 单次不可中断的第三方调用返回后，是否停止领取下一项工作？
- 测试是否覆盖真实并发时序，而不只是直接设置最终状态？

## SkUI 滚动区不能只靠截图缩略图判断横向裁切

### 现象

参数面板没有纵向滚动条时，输入框和下拉框的右边框被裁掉；出现纵向滚动条后，
滚动条又覆盖复选框、输入框和分段按钮。离屏截图整体看起来正常，但放大检查时同样
能看到控件右边框缺失。

### 影响范围

使用 `overflow-y: auto` 的窄侧栏、弹窗和其他固定宽度滚动容器，尤其是内部控件使用
固定宽度或不可收缩 Flex 项时。

### 根因

- `scrollbar-gutter: stable` 在当前 SkUI 布局中没有形成可依赖的内容安全区。
- 滚动条和内容使用同一块右侧区域。
- `overflow-x: hidden` 会把横向溢出直接截掉，使问题看起来像控件本身少画了一条边。
- 只检查整张缩略图，没有检查控件右边框和滚动区的横向范围。

### 解决方案

- 在滚动容器内增加独立内容层，并为内容层固定预留右侧安全距离。
- 允许输入框、下拉框和分段按钮在窄面板中收缩。
- 装饰性元素使用专用类，避免 `.row span { flex: 1 }` 一类宽泛选择器把色块等子元素拉伸。
- 分段按钮文字较长时，为按钮组设置可容纳完整文字的最小宽度，并让整个按钮组换行。
- 滚动容器中的单个 Flex 卡片不能在内容超高时继续收缩；应让卡片按内容自然增高，并用
  `min-height` 保持短内容时铺满视口，否则越界子元素不会计入父级可滚动高度。
- 保持外层只负责滚动，内层负责内容宽度，避免把滚动条避让交给单个控件。

### 验证方式

- 分别渲染无滚动条的短参数面板和有滚动条的长参数面板。
- 放大检查输入框、下拉框、复选框和按钮的完整右边界。
- 通过 `Runtime::scrollStateById()` 断言 `maxScrollX == 0`；长面板同时断言
  `maxScrollY > 0`。

### 快速检查清单

- 滚动条与最右侧控件之间是否有稳定间距？
- 无滚动条时控件右边框是否仍完整？
- 窄窗口下固定宽度控件是否允许收缩？
- 测试是否同时覆盖短内容、长内容和窄窗口？
- 是否检查了 `maxScrollX`，而不只是查看整张截图？

## SkUI 动态参数面板要同时维护事件标记和滚动状态

### 现象

动态生成的分段按钮外观正常但无法点击；勾选参数后面板重新渲染，滚动条会跳回顶部。

### 根因

- SkUI 只把带 `data-action` 的普通按钮作为业务动作节点，只有 `id` 不会产生点击回调。
- `replaceHtmlById()` 替换滚动容器本身时会创建新节点，旧节点的滚动偏移不会继承。
- 在事件回调中替换整个参数面板后立即恢复偏移仍依赖事件收尾和布局时机，不够可靠。

### 解决方案与验证

- 所有动态按钮统一由 helper 写入 `data-action`，并在离屏测试中点击按钮文字区域校验 ID。
- 同一组件的参数变化只替换滚动容器内的 `export-panel-scroll-content`，保留
  `export-panel-body` 节点；切换组件时才重建整个参数面板并从顶部开始。
- 回归测试在按钮点击回调内部替换参数内容，并在事件结束后断言外层滚动容器的
  `scrollY` 仍大于零。

### 范围编辑按钮的点击回归

2026-10-19 范围编辑面板出现相同问题：静态工具按钮和动态区域的选择、定位按钮
只有 `id`，缺少 `data-action`。直接构造 `ElementEvent` 调用处理函数的测试可以通过，
但用户鼠标点击不会触发处理函数。

- 静态按钮和动态 HTML 都必须带动作标记；表单输入的 `Input` / `Change` 事件不能
  作为普通按钮是否可点击的证明。
- `PreviewRangeEditorTest` 使用与宿主相同的 `Win32EventAdapter`，先处理 UI，再将
  未消费的消息交给控制器。控件更新后先布局，再发送鼠标按下、抬起消息。
- 回归先复现关闭按钮无响应，再验证工具切换、绘制、动态列表、命名、删除、
  撤销重做、应用、取消及 150% 缩放下的按钮点击。
- 当前 SkiaUI 0.1.15 的接口约束见上游 `docs/skui_css_dom_support.md` 的按钮、
  `data-action` 和事件部分；排查时先检查动作标记，再检查命中坐标、宿主消息顺序。

### 数值输入右对齐时的光标与选区错位

2026-10-20 正方形下载区半径框出现数字在右侧、光标和高亮在左侧的现象，
鼠标选字与替换输入因此无法对应。影响新增半径框的鼠标编辑，Ctrl+A 全选替换
仍能成功，所以只测全选会漏掉问题。

- 当前 SkiaUI 0.1.15 的 `text-align` 文档只声明适用于普通文本。项目所用源版本
  `854bab8ea619e3767b588de823b20ac4a81c4f6d` 中，`textStartX()` 和鼠标命中会考虑
  右对齐，但 `inputCaretRect()`、`drawInputSelection()` 仍从内容区左侧计算坐标。
- 最小复现先渲染实际页面，从像素找到首位数字，再点击数字前方：
  修复前数字起点为 208，`editingCaretRect().x` 为 101；选区偏移虽为 0，
  光标仍没有出现在数字旁。两次运行均复现，排除了只检查选区偏移的假通过。
- 只将半径框的 `text-align` 改为 `left` 后，原用例通过；同版本
  `setValueById()` 遇到相同文本会直接返回，无需为此改动页面刷新或地图消息路由。
- `PreviewRangeEditorTest` 保留字形与光标坐标校验，并通过 Win32 鼠标消息拖选
  首位数字、替换、回车和撤销；覆盖 100%、150% 缩放和窄窗口。
  全选替换、失焦提交、无效值和重新打开后的半径恢复继续单独验证。
- 后续检查输入框时，要同时比较文字、鼠标命中、光标和选区的坐标；
  不应把普通文本对齐支持等同于完整的可编辑控件对齐支持。运行时调用和渲染
  保持在现有 UI 线程，布局完成后再发送鼠标消息；测试截图保留在 `tmp/`。

## Cesium 建筑近景模糊要区分选层、选图和编码

### 现象与影响

3D Tiles 建筑在贴近墙面时仍像低分辨率合并图，FBX 则能按原规则使用合适散图。
问题只影响新增 3D Tiles 选图分支，原 FBX 的选图和 XYZ DOM 不受影响。

### 根因与定位

- 格式写入回调被同时用作“采用另一套选图算法”的开关。
  新分支按 `(uid ^ seed) % textureCount` 取余，绕过尺寸匹配。
- 真实附近缓存中 10,467 条建筑记录的 UID 全为 0，默认种子也为 0，
  因此墙体和屋顶均退化为固定使用图库第一张。
- 墙体首张源 JPG 只有 64×64。相机距目标墙 50、5、0.5 米时，
  屏幕中心拾取均为最细层、几何误差为 0，材质引用独立散图而不是图集。
- 固定网格、UV、相机和时间，只将 KTX2 换回原始 JPG，近景仍同样模糊。
  测试区域中 KTX2 与原生解码 PNG 像素完全一致；
  原 JPG 对 KTX2 的 RGB 平均绝对误差为 2.513/255。
  这些是本机浏览器对照数据，不代表所有显卡转码目标的像素完全相同。

### 解决方案

- 格式写入只决定 FBX 或 GLB，不再决定选图规则。
- 两条路径统一调用原来的楼高候选、墙长加权、材质桶复用和屋顶比例选择。
- 在分块、轮廓简化前计算一次整批选图，按源记录索引传递到各瓦块、各级 LOD。
  源索引只作为本次导出内的稳定关联，不伪造服务端 UID，也不新增持久化缓存。
- 无效建筑保留空选图槽；数量、图库索引及屋顶模式不匹配时报错，
  不静默回退到图库首张。取消不会覆盖已完成的选图结果。
- 叶层维持原散图和 UV 规则；粗层只负责简化、烘焙与合并，不重新选图。

### 回归与快速检查

- `CesiumExportTest` 构造全零 UID 和不同尺寸图库，对比真实 FBX 导出与叶层
  散图的内容摘要。修复前能够失败，不只验证文件存在或浏览器无报错。
- 另覆盖分块重排、轮廓简化、无效源记录、错误索引与选图取消。
- 浏览器不能只断言“视野中有叶瓦块”；应拾取问题像素所在的实际内容，
  再检查该材质引用图集还是散图，以及原始图片尺寸。
- 合成数据必须包含缺失或重复身份字段，不能只使用非零唯一 UID。
- 不通过调低 SSE、放大源图或修改压缩格式掩盖源图选择错误。

## FBX 与 UE 地理参考坐标的实际导入对照

### 现象与根因

2026-10-29 核对 `FGISToolGeoReferencingData` 时发现，下载器的平面模型使用
Web Mercator，UE 参照脚本的 `ProjectedCRS` 则默认使用 EPSG:32650。
相同中心只能消除原点平移，不能消除两种投影的距离与方向差异。
影像瓦片使用 EPSG:3857，不代表所有消费端默认也使用这套模型投影。

球面模式都经过 WGS84 ECEF 和中心 ENU，但下载器先将零高度表面转换到 ENU，
再把高度加到中心坐标系的 Z；参照脚本将各点高度参与 ECEF 转换。
因此零高度表面可一致，非零高度时不能认定两者严格等价。
本次仅验证并记录差异，未改变任何导出转换算法。

### 验证方法

- 在 UE 5.5.4 中实际调用 `AssetEditorTool_MHJX` 的 `DomDownImport::Import`，
  使用插件原有 `UFbxFactory`、场景转换和单位转换设置。
- 临时编译原始 `GISToolGeoReferencing.h/.cpp` 和 `PROJConvert.h/.cpp`，
  文件摘要与参照项目原文件一致；使用原插件的 PROJ 9.5.1 和坐标库。
  测试后移除临时源码与构建配置，并重建插件。
- 网格由下载器现有核心库生成，不以手工 FBX 代替导出链路。
  根据贴图像元范围和 UV 求出每个样点的经纬度，再调用参照脚本求预期 UE 位置。
- 北京中心 `(116.415799, 39.888175)`、上海中心 `(121.473701, 31.230416)`，
  分别覆盖平面/球面、零高度/120 米高度、合并/独立网格，共 16 组。
  中心高度和世界原点偏移均为零，平面对照设为 EPSG:3857。
- 对导入网格顶点集合与预期位置集合计算双向最近点最大距离，
  同时检查实际导入位置与源 FBX 的 `(X, -Y, Z)` 是否一致。
  使用 EPSG:32650 额外计算平面对照，避免同一套公式自证。

### 实测结果

| 样例 | 平面与 3857 脚本最大误差 | 零高度球面最大误差 | 120 米球面最大误差 |
| --- | --- | --- | --- |
| 北京 | 0.015234 厘米 | 0.012410 厘米 | 3.902267 厘米 |
| 上海 | 0.006914 厘米 | 0.013250 厘米 | 5.128110 厘米 |

合并与独立导入的结果相同。实际导入位置与源 FBX 的 `(X, -Y, Z)` 的
最大差异为零，说明该插件已正确执行轴转换，不应再次手工翻转 Y。
本组样例改用 UTM50 的平面对照时，最大位置差分别约 633.052 米和 474.002 米；
该数字只描述本组范围，不是其他区域的固定误差。

### 使用条件与快速检查

- 平面对齐需统一 `PlanetShape=Plane`、`ProjectedCRS=EPSG:3857` 和完整精度的
  WGS84 中心经纬度；本次对应 `OriginAltitude=0`。
- 改变投影配置后需重新 `Init()`；`CheckAndInit()` 不负责检测已初始化参数的变化。
- 检查输入高度的参考基准。试验使用同一个数值高度，不包含 EGM2008 与椭球高换算。
- 使用导入插件既有轴转换，Actor 保持相同位置、旋转和缩放。
  顶点一致不代表任意 Actor 变换或世界原点偏移都会自动匹配。
- 对球面高度要求严格一致时，应先统一经纬高到 ECEF 的处理，再验证大范围与高建筑。
  本次未覆盖非零中心高度、世界原点移动、建筑网格或极区输入。
- 原始数值报告和测试入口属于本机验证产物，位置记在
  `tmp/local-environment/ue-coordinate-validation.md`，不提交临时引擎源码与资产。

### 球面扩大范围验证

同日进一步通过原导入插件测试 64 份真实球面 FBX，分别合并和独立导入，
共 128 组，检查 16506 个导入顶点和 21420 个三角面重心。
覆盖北京、上海、赤道 `(30, 0)`、北纬 70 度 `(20, 70)`、悉尼
`(151.2093, -33.8688)`，层级 18/15/12/10，高度 0/120/1000 米，
另加负 100 米、零高程自适应地形、细分 1 和 16 的对照。
所有中心高度、世界原点偏移仍为零；每份样例使用中心附近 3×3 源瓦片、
512 贴图、默认细分 4。自适应地形采样率为 2000 米、每块上限 100 三角面。
测试未调整生产转换算法，也未保存测试资产。

顶点误差与面内采样误差必须分开描述：

- 顶点：以源 FBX 位置匹配实际导入顶点，再与原脚本的同经纬高位置比较；
  同时检查导入位置与源 FBX 的轴转换是否一致。
- 面内：比较实际导入三角面重心，与其重心 UV 对应经纬高在原脚本中的位置。
  这是重心采样最大偏差，不是整张曲面所有位置的严格误差上界，
  也不是点到三角面的最近距离。

北京样例的顶点结果如下，距离为顶点到中心的最远水平距离：

| 最远距离 | 0 米高度误差 | 120 米高度误差 | 1000 米高度误差 |
| --- | --- | --- | --- |
| 约 0.260 千米 | 0.001685 厘米 | 0.489853 厘米 | 4.080659 厘米 |
| 约 2.078 千米 | 0.012410 厘米 | 3.902267 厘米 | 32.586613 厘米 |
| 约 17.178 千米 | 0.090813 厘米 | 32.292774 厘米 | 269.481694 厘米 |
| 约 80.556 千米 | 0.468031 厘米 | 151.661807 厘米 | 1263.884382 厘米 |

上述误差包含导入网格浮点位置的精度影响。全部区域的零高度顶点误差最大
0.468031 厘米；最大范围样例位于赤道，最远约 101.48 千米，120 米和
1000 米高度的顶点误差分别为 1.916128 米和 15.973066 米。
高度误差主要在水平分量上，近似随高度与离中心距离的乘积增长。
把实际顶点与“原脚本零高度位置 + 局部 Z 高度”比较后，最大剩余差仅
0.468031 厘米，支持高度处理差异这一根因。
全部轴转换对照误差为零；球面模式将 `ProjectedCRS` 从 3857 换成 32650
也没有改变结果，说明换平面 CRS 无法消除球面高度差异。

同时发现，顶点坐标准确不能保证三角面内部贴合椭球：

| 北京同一约 80.556 千米范围、零高度 | 三角面数 | 重心采样最大偏差 |
| --- | --- | --- |
| 关闭高程，细分 1 | 18 | 136.266 米 |
| 关闭高程，细分 4 | 288 | 8.549 米 |
