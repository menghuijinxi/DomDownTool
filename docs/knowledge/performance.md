# 性能问题复盘

## 低层级瓦片修复阻塞下载循环

- 现象：下载大量腾讯卫星图占位图时，整体网络速度长期只有几百 KB/s，任务管理器里网络流量明显不稳定。
- 影响范围：带占位图降级修复的地图下载流程，尤其是目标层级连续命中占位图时。
- 根因：普通瓦片使用 `curl_multi` 并发下载，但占位图修复路径里曾使用同步 `curl_easy_perform` 下载低层级父瓦片。只要进入修复路径，主下载循环就会被同步网络 I/O 占住，已有并发连接无法持续推进。
- 解决方案：把低层级父瓦片下载封装为内部 `CurlRequestType::RepairParent` 请求，继续进入同一个 `curl_multi` 队列；父瓦片下载完成后一次性切出它覆盖的整组目标层级瓦片并写入硬盘缓存。
- 验证方式：Debug 和 Release 构建均通过；代码中不再保留 `curl_easy_perform` 同步下载路径，也没有新增每瓦片线程。
- 快速检查清单：遇到下载速度异常时，先确认耗时路径是否绕开了 `curl_multi`；确认内部修复请求不计入用户目标下载总量；确认父瓦片缓存命中后会批量生成子瓦片，而不是每个子瓦片重复下载同一个父瓦片。

## 缓存检测与漏瓦片排查

- 现象：拼接结果里偶尔出现空洞，但下载流程没有明显错误提示；重新运行时需要等完整流程跑很久才知道哪些缓存有问题。
- 影响范围：已有大量缓存、且同时存在缺失文件、占位图、损坏文件或低层级修复失败的下载任务。
- 根因：下载前只在逐个 `DownloadTile()` 时串行判断缓存状态；批量低层级修复只要部分子瓦片写入成功就可能被视为成功，失败子瓦片没有被集中报告。
- 解决方案：下载前按目标瓦片列表分块并行扫描缓存，统计可用、缺失、占位图、无效文件并打印样例；下载结束后再次扫描同一目标列表，仍不可用的瓦片集中报告。缓存扫描使用固定 worker 池按批次处理 I/O，worker 数由 `std::thread::hardware_concurrency()` 推导，不依赖 OpenCV 的 CPU 并行线程数，也不写死固定线程数。批量修复必须整组目标子瓦片全部可用才返回成功。GCJ02 偏移展开后的瓦片列表必须先按 `z/x/y` 去重，否则相邻瓦片的重叠 offset 范围会把检测量放大数倍。
- 快速检查清单：先看“下载前缓存检测”的缺失/占位/无效数量，再看“下载后缓存检测”是否仍有待处理瓦片；如果下载后仍有缺失，优先检查对应路径是否被占用、低层级父瓦片是否也为占位图、以及磁盘写入是否失败。

## 后处理缓存跨项目污染导致大图空白

- 现象：大图或 `Google_墨卡托` 金字塔中出现成片的透明黑块，形状通常沿瓦片边界扩散；源下载缓存看起来完整，且重新下载本次区域后问题仍可能存在。
- 影响范围：多个下载项目共用同一个 `CachePath`，并使用默认后处理目录
  `CachePath/Google_墨卡托` 的场景。该目录会跨项目保留各层级的后处理瓦片。
- 根因：后处理最高层级瓦片目前以“目标 PNG 存在且可解码”作为缓存命中条件，不记录其所属下载项目或源瓦片覆盖范围。遗留瓦片即使只由上个项目的一部分源数据生成，也可能在本次任务中被直接复用。随后向低层级合成父瓦片时，遗留子瓦片会继续参与合成，透明区域被逐级缩小并传递到大图。
- 已确认样例：`cache/百度地图/Google_墨卡托/15/26984/12414.png` 的顶部空白和
  `15/26984/12416.png` 的底部空白，沿 `z15 -> z14 -> z13 -> z12` 父瓦片链均可复现；
  对应文件时间为旧项目的 `2026-06-28`，而本次任务重新生成的相邻瓦片时间为
  `2026-07-25`。这说明问题来自遗留后处理缓存，而不是当前下载的 `cache/百度地图/17`
  源瓦片缺失。
- 快速定位方法：从大图中的空白区域找一个对应的 `Google_墨卡托/{z}/{x}/{y}.png`，依次检查
  其四个子瓦片 `{z + 1}/{2x 或 2x + 1}/{2y 或 2y + 1}.png`，直到本次任务的最高层级。
  如果空白在父子链中持续存在，且其中瓦片的修改时间早于本次任务或与当前源缓存时间不一致，
  即可判定为跨项目遗留缓存。不要只根据 PNG 存在或能解码来判断它属于本次任务。
- 处理策略：默认行为不强制重生成，以保留缓存复用性能。需要隔离任务时，为不同项目设置不同的
  `PostProcessOutputPath`；需要修复已有结果时，仅清理受影响项目的后处理输出目录或已定位的
  瓦片父子链后重新运行，保留 `CachePath/{z}` 下的原始下载缓存。

## DX12 GIS 首次显示卡顿与边缘锯齿

- 现象：GIS mesh 提交后的持续绘制很流畅，但新的大范围 mesh 首次显示时 UI 会明显掉帧；
  面、宽线和兴趣点边缘还有明显锯齿。
- 影响范围：`Dx12GisRenderer` 绘制百万级顶点和索引的 GIS 叠加层时，尤其是切换数据范围或
  源缩放层级后的第一帧。
- 根因：CPU mesh 虽然在线程中生成，DEFAULT/UPLOAD buffer 的创建、`Map`、全量
  `memcpy` 和 `CopyBufferRegion` 原先仍在 UI 绘制帧中执行。后续每帧只有少量 draw call，
  因此稳定绘制不是瓶颈。锯齿则来自单采样 back buffer 和点 shader 的硬 `clip`，与 draw call
  数量无关。
- 解决方案：GIS 先绘制到独立的透明 4x MSAA render target，不支持 4x 时降为 2x/1x；
  Resolve 到单采样纹理后，以预乘 alpha 合成到 Skia back buffer。点使用导数覆盖率平滑圆形
  边缘。GPU buffer 在后台线程通过独立 Copy Queue 创建和提交，Direct Queue 只插入 GPU
  fence wait 和 COPY_DEST 到顶点/索引状态的 barrier，不做 CPU fence wait。上传期间继续绘制
  上一组 GPU mesh，并按源缩放层级换算坐标。
- 生命周期约束：上传任务必须持有 CPU mesh 的共享所有权；UPLOAD、DEFAULT buffer、Copy
  Queue、allocator、command list 和 fence 至少保留到使用它们的 Direct Queue 帧 fence 完成。
  设备或数据代际变化时，旧上传结果只能丢弃内容，不能提前释放仍在 Copy Queue 中使用的资源。
- 验证方式：Release 构建通过，`GisOverlayRendererTest` 和 `GisMeshBuilderTest` 通过；运行日志
  中通过 `dx12_draw_succeeded` 的 `msaa` 字段确认采样数，通过
  `dx12_background_upload_ready` 的字节数和提交耗时确认后台上传路径。
- 快速检查清单：首次显示掉帧时先区分 CPU mesh 生成、CPU 到上传堆拷贝和稳定 draw 的耗时；
  检查 UI 线程是否调用 `Map`/`memcpy`/`CreateCommittedResource`；检查 Copy Queue 与 Direct
  Queue 是否只做 GPU fence 同步；检查 PSO 的 `SampleMask` 是否显式设置为
  `D3D12_DEFAULT_SAMPLE_MASK`；检查 Resolve 前后资源状态及预乘 alpha blend 是否匹配。
