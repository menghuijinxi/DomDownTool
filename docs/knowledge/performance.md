# 性能问题复盘

## 高频鼠标消息饿死地图重绘

- 现象：地图单帧绘制和 GPU 提交都只需数毫秒，但高频鼠标拖拽时画面会数百毫秒不更新，随后
  一次跳到新位置。
- 根因：宿主地图控制器持有鼠标 capture 时，每个 `WM_MOUSEMOVE` 只请求异步窗口失效。
  `WM_PAINT` 是低优先级消息，在约 500 Hz 的连续鼠标输入下会长期得不到调度。SkiaUI 对自身
  控件的 capture 有即时重绘分支，但宿主控制器的地图拖拽不会进入该分支。
- 解决方案：地图视口实际变化后投递一个可合并的即时重绘消息。宿主窗口先在原鼠标回调返回后
  标记帧为 dirty，再由该消息通过 `RDW_UPDATENOW` 同步完成一帧。即时帧以短间隔合并重复输入，
  最终由 `Present1(1)` 对齐显示器；D3D 全帧绘制不请求额外的 GDI 背景擦除。拖拽期间的经纬度
  状态栏限制为 20 Hz，避免每个约 500 Hz 的鼠标事件都修改文本；同一次状态刷新中的多个 DOM
  修改还必须使用 `skui::RuntimeUpdateBatch` 合并布局。普通悬停、状态栏刷新和动画仍使用异步失效。
- 验证方式：同时启用 `SKIATEST_FRAME_PACING_CSV` 和 `SKIATEST_PERF_CSV`，手动连续拖拽地图。
  修复前一次呈现可积压 450 个输入，首输入延迟最高约 980 ms，而实际帧工作耗时不超过 7.3 ms；
  修复后拖拽期间应持续产生 `frame_presented`，且输入延迟不再随鼠标消息持续累积。

## 未批处理的 UI 状态刷新造成周期性长帧

- 现象：地图连续拖拽时大部分时间流畅，但每隔约一到两秒会突然停顿一帧。增加导出页、任务页等
  UI 后问题更明显；回退到较小的旧界面仍会偶发，只是总体帧率较高，因此不容易察觉。
- 根因：`MapRenderer::draw()` 检测到瓦片缓存或下载统计变化后会调度一次完整 `updateUi()`。
  该函数会连续调用多次 `setTextById()`、`setValueById()`、`setVisibleById()` 和属性更新。
  SkiaUI 在不处于更新批次时会在每个 setter 结束后立即刷新布局，因此一次逻辑状态刷新会重复计算
  整棵 DOM。隐藏页面也会增加 DOM 规模，使新增界面后每次布局变慢。拖拽坐标刷新中的多个文本
  setter 存在同样问题。
- 诊断证据：120 Hz 显示器的单帧预算约为 8.33 ms。性能追踪中，一次状态刷新连续产生二十多条
  `style_recompute` / `recompute_layout_total`，每次约 0.8-1.1 ms，合计形成约 20-25 ms 的主线程
  空窗；同期真正的地图绘制通常只有约 1 ms。这个特征可以把 UI 重复布局与瓦片解码、GIS mesh
  上传或单纯帧率偏低区分开。
- 解决方案：在 `PreviewController::updateUi()` 和 `updateMapInteractionUi()` 入口创建
  `skui::RuntimeUpdateBatch`。RAII 批次覆盖函数内的所有 setter 和提前返回路径，在函数结束时只做
  一次布局。刷新频率节流与更新批处理解决的是不同问题，二者都需要保留：节流减少逻辑刷新次数，
  批处理消除一次刷新内部的重复布局。
- 编码约束：一个逻辑操作只要会修改两个或更多 Runtime 元素，就应先建立
  `skui::RuntimeUpdateBatch`，尤其是定时刷新、后台任务完成、缓存统计变化和页面切换路径。不要依赖
  调用者恰好已经开启批次；批次允许嵌套，叶子级批量更新函数应自行保护其事务边界。
- 快速定位步骤：
  1. 先看帧追踪：输入延迟持续增长通常是 `WM_PAINT` 饥饿；间隔稳定但周期性出现 16-30 ms
     空窗通常是主线程长任务。
  2. 再看性能追踪：在空窗附近搜索连续的 `recompute_layout_total`。一次逻辑刷新应最多产生一次
     该事件；连续十几或几十次说明缺少更新批次。
  3. 如果布局只有一次，再检查 `draw_ganesh_callback`、`ganesh_flush_submit`、`wrap_backbuffer` 和
     GIS 上传事件，区分 CPU 绘制、GPU 提交与交换链等待。
  4. 修改界面后必须在 Release 构建中连续拖拽地图至少十秒，覆盖瓦片统计变化和后台完成通知，
     不能只观察静止页面或短距离拖动。
- 追踪注意事项：主观 A/B 对比不要设置 `SKIATEST_PERF_FLUSH=1`。逐条同步 `fflush` 会显著改变
  消息循环负载，而且布局次数更多的版本受影响更大。本次误用时旧版写入约 19.4 MB、219627 条
  性能记录，最新版约 6.7 MB、72235 条，导致旧版异常卡顿，数据不具可比性。正常对比应关闭性能
  追踪；需要采样时优先只启用帧追踪，或关闭逐条 flush 并正常退出程序以刷新缓冲区。

## 低层级瓦片修复阻塞下载循环

- 现象：下载大量腾讯卫星图占位图时，整体网络速度长期只有几百 KB/s，任务管理器里网络流量明显不稳定。
- 影响范围：带占位图降级修复的地图下载流程，尤其是目标层级连续命中占位图时。
- 根因：普通瓦片使用 `curl_multi` 并发下载，但占位图修复路径里曾使用同步 `curl_easy_perform` 下载低层级父瓦片。只要进入修复路径，主下载循环就会被同步网络 I/O 占住，已有并发连接无法持续推进。
- 解决方案：把低层级父瓦片下载封装为内部 `CurlRequestType::RepairParent` 请求，继续进入同一个 `curl_multi` 队列；父瓦片下载完成后一次性切出它覆盖的整组目标层级瓦片并写入硬盘缓存。
- 验证方式：Debug 和 Release 构建均通过；代码中不再保留 `curl_easy_perform` 同步下载路径，也没有新增每瓦片线程。
- 快速检查清单：遇到下载速度异常时，先确认耗时路径是否绕开了 `curl_multi`；确认内部修复请求不计入用户目标下载总量；确认父瓦片缓存命中后会批量生成子瓦片，而不是每个子瓦片重复下载同一个父瓦片。

## 超大范围导出触发无效回退和进度通知风暴

- 现象：半径 500 公里、z15 等百万瓦片任务开始后，进度在几秒内虚增到几十万，任务页随后
  无法正常交互；缓存中只新增少量有效文件和多个零字节低层级文件。
- 影响范围：卫星服务器返回不可用瓦片或请求快速失败，并启用低层级父瓦片修复的超大范围任务。
- 根因：待下载目标会把任意层级的父瓦片修复请求视为覆盖自身，即使父子层级差对应的展开量已
  超过 `MaxBatchRepairedTileCount`，真正修复阶段必然拒绝。被覆盖的目标仍被提前计为完成，并且
  每个进度变化都会通知任务页重建列表。一个 z2 到 z15 的无效父请求因此可以造成几十万次虚假
  进度和 UI 刷新。
- 解决方案：排队父瓦片、判断待修复覆盖和实际展开统一使用同一个批量上限；目标等待可执行的
  父瓦片请求结束后重新检查缓存，不提前计数。任务进度在内存中持续更新，但界面通知限制为阶段
  变化、完成节点或每 100 毫秒一次。单个瓦片请求设置 10 秒连接超时和 20 秒总超时，避免等待
  修复请求永久占住下载循环。
- 验证方式：本地不可用瓦片回归测试确认 z15 最低只回退到 z9，对应最多展开 4096 张；模拟一次
  导出连续上报 20000 次进度，任务仍完成且界面状态通知不超过 10 次。用户样例任务记录中的
  `1,143,807` 张目标瓦片和 `214,828` 虚假完成数可用于核对同类问题。
- 快速检查清单：先比较任务记录的完成数与同层级有效缓存文件数；检查是否存在跨度过大的待修复
  父请求；确认“可作为覆盖”与“实际允许展开”使用同一限制；确认高频工作进度没有逐项触发 DOM
  重建；确认网络请求有明确超时，且取消期间等待循环可以退出。

## 缓存检测与漏瓦片排查

- 现象：拼接结果里偶尔出现空洞，但下载流程没有明显错误提示；重新运行时需要等完整流程跑很久才知道哪些缓存有问题。
- 影响范围：已有大量缓存、且同时存在缺失文件、占位图、损坏文件或低层级修复失败的下载任务。
- 根因：下载前只在逐个 `DownloadTile()` 时串行判断缓存状态；批量低层级修复只要部分子瓦片写入成功就可能被视为成功，失败子瓦片没有被集中报告。
- 解决方案：下载前按目标瓦片列表分块并行扫描缓存，统计可用、缺失、占位图、无效文件并打印样例；下载结束后再次扫描同一目标列表，仍不可用的瓦片集中报告。缓存扫描使用固定 worker 池按批次处理 I/O，worker 数由 `std::thread::hardware_concurrency()` 推导，不依赖 OpenCV 的 CPU 并行线程数，也不写死固定线程数。批量修复必须整组目标子瓦片全部可用才返回成功。GCJ02 偏移展开后的瓦片列表必须先按 `z/x/y` 去重，否则相邻瓦片的重叠 offset 范围会把检测量放大数倍。
- 快速检查清单：先看“下载前缓存检测”的缺失/占位/无效数量，再看“下载后缓存检测”是否仍有待处理瓦片；如果下载后仍有缺失，优先检查对应路径是否被占用、低层级父瓦片是否也为占位图、以及磁盘写入是否失败。

## 后处理缓存跨项目污染导致大图空白

- 现象：大图或 `Google_墨卡托` 金字塔中出现成片的透明黑块，形状通常沿瓦片边界扩散；源下载缓存看起来完整，且重新下载本次区域后问题仍可能存在。
- 影响范围：多个下载项目共用同一个 `CachePath`，并使用默认后处理目录
  `CachePath/Google_墨卡托` 的场景。该目录会跨项目保留各层级的后处理瓦片。
- 根因：后处理最高层级瓦片目前以“目标 PNG 存在且可解码”作为缓存命中条件，不记录其所属下载项目或源瓦片覆盖范围。遗留瓦片即使只由上个项目的一部分源数据生成，也可能在本次任务中被直接复用。随后向低层级合成父瓦片时，遗留子瓦片会继续参与合成，透明区域被逐级缩小并传递到大图。
- 已确认样例：`cache/百度地图/Google_墨卡托/15/26984/12414.png` 的顶部空白和
  `15/26984/12416.png` 的底部空白，沿 `z15 -> z14 -> z13 -> z12` 父瓦片链均可复现；
  对应文件时间为旧项目的 `2026-06-28`，而本次任务重新生成的相邻瓦片时间为
  `2026-07-25`。这说明问题来自遗留后处理缓存，而不是当前下载的 `cache/百度地图/17`
  源瓦片缺失。
- 快速定位方法：从大图中的空白区域找一个对应的 `Google_墨卡托/{z}/{x}/{y}.png`，依次检查
  其四个子瓦片 `{z + 1}/{2x 或 2x + 1}/{2y 或 2y + 1}.png`，直到本次任务的最高层级。
  如果空白在父子链中持续存在，且其中瓦片的修改时间早于本次任务或与当前源缓存时间不一致，
  即可判定为跨项目遗留缓存。不要只根据 PNG 存在或能解码来判断它属于本次任务。
- 处理策略：默认行为不强制重生成，以保留缓存复用性能。需要隔离任务时，为不同项目设置不同的
  `PostProcessOutputPath`；需要修复已有结果时，仅清理受影响项目的后处理输出目录或已定位的
  瓦片父子链后重新运行，保留 `CachePath/{z}` 下的原始下载缓存。

## DX12 GIS 首次显示卡顿与边缘锯齿

- 现象：GIS mesh 提交后的持续绘制很流畅，但新的大范围 mesh 首次显示时 UI 会明显掉帧；
  面、宽线和兴趣点边缘还有明显锯齿。
- 影响范围：`Dx12GisRenderer` 绘制百万级顶点和索引的 GIS 叠加层时，尤其是切换数据范围或
  源缩放层级后的第一帧。
- 根因：CPU mesh 虽然在线程中生成，DEFAULT/UPLOAD buffer 的创建、`Map`、全量
  `memcpy` 和 `CopyBufferRegion` 原先仍在 UI 绘制帧中执行。后续每帧只有少量 draw call，
  因此稳定绘制不是瓶颈。锯齿则来自单采样 back buffer 和点 shader 的硬 `clip`，与 draw call
  数量无关。
- 解决方案：GIS 先绘制到独立的透明 4x MSAA render target，不支持 4x 时降为 2x/1x；
  Resolve 到单采样纹理后，以预乘 alpha 合成到 Skia back buffer。点使用导数覆盖率平滑圆形
  边缘。GPU buffer 在后台线程通过独立 Copy Queue 创建和提交，Direct Queue 只插入 GPU
  fence wait 和 COPY_DEST 到顶点/索引状态的 barrier，不做 CPU fence wait。上传期间继续绘制
  上一组 GPU mesh，并按源缩放层级换算坐标。
- 生命周期约束：上传任务必须持有 CPU mesh 的共享所有权；UPLOAD、DEFAULT buffer、Copy
  Queue、allocator、command list 和 fence 至少保留到使用它们的 Direct Queue 帧 fence 完成。
  设备或数据代际变化时，旧上传结果只能丢弃内容，不能提前释放仍在 Copy Queue 中使用的资源。
- 验证方式：Release 构建通过，`GisOverlayRendererTest` 和 `GisMeshBuilderTest` 通过；运行日志
  中通过 `dx12_draw_succeeded` 的 `msaa` 字段确认采样数，通过
  `dx12_background_upload_ready` 的字节数和提交耗时确认后台上传路径。
- 快速检查清单：首次显示掉帧时先区分 CPU mesh 生成、CPU 到上传堆拷贝和稳定 draw 的耗时；
  检查 UI 线程是否调用 `Map`/`memcpy`/`CreateCommittedResource`；检查 Copy Queue 与 Direct
  Queue 是否只做 GPU fence 同步；检查 PSO 的 `SampleMask` 是否显式设置为
  `D3D12_DEFAULT_SAMPLE_MASK`；检查 Resolve 前后资源状态及预乘 alpha blend 是否匹配。

## FBX 高程网格固定细分、漏峰和块间接缝

- 现象：启用 DEM 高程导出后，平地仍生成完整规则网格，山顶细节却不足；不同物理范围的块可能使用
  相同面数，块边界还会在 Unreal 中形成明显裂缝。边缘贴图块可能包含任务范围外的模型。
- 根因：固定 `FbxMeshSubdivision` 不随物理尺寸变化；只检查四角、边中点和中心的顶向下误差会漏掉
  内部窄山脊与孤立山峰。每个贴图块独立决定四叉树边界，导致相邻块共享边上的顶点集合不同；单块内
  不同细分层级也会形成 T 型边。
- 解决方案：先按用户设置的米制采样率建立完整高度场，再检查节点内所有样本相对于双线性面的最大误差，
  使平坦区域保持粗网格、变化区域继续细分。网格先裁剪到请求范围，部分块按实际范围减少采样段数；
  单块叶节点汇总同一直线的全部分割点，相邻块在三角化前合并共享边分割点，统一消除 T 型接缝。
- 验证方式：`PostProcessFbxTest` 检查顶点不超出范围、平坦 DEM 面数减少、变化 DEM 面数增加、内部孤立
  山峰被保留、降低采样间距会增加面数、内部边成对闭合，以及相邻 mesh 共享边的位置和高度逐点一致。
  `CopernicusDemTest` 和 `ExportTaskManagerTest` 验证高程缓存及任务参数恢复未回归。
- 快速检查清单：比较平坦与山地面数；确认采样率按米制范围计算，而非每块固定顶点数；检查内部尖峰是否
  出现在完整高度场；比较相邻 mesh 共享边的顶点序列与高度；最后核对边缘网格包围盒未越过请求范围。

## FBX 法线和合并贴图接缝

- 现象：Unreal 等导入器中，FBX 瓦片边界出现一条明暗线；同一批卫星瓦片直接查看没有接缝，但导出
  的合并大图或 FBX 贴图在横纵瓦片边界出现亮暗块。
- 根因：原 FBX 网格没有写入 `mNormals`，导入器会按每个独立 mesh 分别重算法线，跨 mesh 的共享边
  因此无法平滑。原大图合并逻辑对每个瓦片独立 `resize`，插值只能读取当前瓦片的边缘像素，无法读取
  相邻瓦片，导致边界重复采样。FBX 纹理生成还会受到非整数纹理范围偏移的影响，同样不能逐瓦片缩放。
- 解决方案：导出前收集所有 mesh 的三角形面法线，按共享平面位置跨瓦片累加并归一化，再显式写入
  Assimp `aiMesh::mNormals`。大图和 FBX 纹理都先按全局瓦片坐标拼成连续采样画布，再对完整画布做一次
  仿射采样；请求范围外的 FBX 纹理像素最后清零 alpha。采样尺寸与输出尺寸相同且范围为整数时直接使用
  画布视图，避免额外分配大图内存。
- 验证方式：`PostProcessFbxTest` 检查所有 mesh 带法线，并检查相邻共享边法线点积不低于 0.999；
  `PostProcessMergedImageTest` 使用跨瓦片高频样本，比较一次性缩放参考图，确保边界最大误差不超过 16。
- 快速检查清单：先确认 FBX 导入后 mesh 有法线；再比较共享边顶点位置、法线点积；贴图或大图缩放时确认
  输入是完整连续画布而不是逐瓦片 `resize`；最后确认请求范围外仍保持透明。

## 低级别回退瓦片污染标准缓存导致预览混级

- 现象：同一范围的高德卫星预览中，一部分区域是目标层级的清晰瓦片，另一部分区域是被放大的低级别瓦片；
  任务页可能显示没有新增读取或下载，但画面仍然混级。导出大图和 FBX 也可能复用这类错误缓存。
- 影响范围：卫星服务器返回不可用瓦片、请求失败或启用父级瓦片回退的任务，尤其是复用旧缓存的预览任务。
- 根因：旧逻辑把低级父瓦片裁切放大后直接写入目标层级的 `z/x/y.png`，并在目标层级请求前把该文件视为已下载。
  预览端只按路径读取，无法知道文件实际来自哪个层级，因此把回退图当成真实目标瓦片。历史污染文件还会让后续任务
  在网络请求之前命中错误缓存。
- 排查路径：先查看任务日志的“读取/下载”计数；如果画面混级但两项均为零，检查目标层级目录是否存在由旧任务生成的文件。
  再对照文件修改时间和请求层级，确认是否存在低级父瓦片裁切后的目标路径文件。不要仅凭 PNG 尺寸判断来源层级，放大后的
  回退图与真实瓦片尺寸相同。
- 解决方案：低级回退图写入独立的 `CachePath/fallback/<zoom>/<x>/<y>.png`，永远不占用标准 `z/x/y` 缓存；目标层级
  下载前只检查标准缓存，必须先尝试真实目标层级请求。服务器明确返回不可用瓦片后，删除无效标准文件，再生成 fallback。
  后处理读取时优先使用真实标准瓦片，标准瓦片无效时才使用 fallback；下载前扫描不把 fallback 计为真实命中，下载后扫描可以
  将 fallback 作为可用降级结果，保证导出仍能完成。
- 高德卫星缓存隔离：卫星预览使用 `cache/高德地图/卫星图`，电子地图和透明路网路径保持不变。旧的
  `cache/高德地图` 不自动删除，避免破坏用户已有数据；首次使用新目录会重新请求真实目标层级。
- 验证方式：`PostProcessPyramidTest` 覆盖“已有父级缓存仍发起目标层级请求、回退图只写入 fallback、后处理可读取 fallback”
  三个条件；高德 URL 测试确认卫星使用独立缓存目录。手动复现时清空或改名新的 `cache/高德地图/卫星图` 后重新查看同一范围，
  应能看到目标层级请求重新发生，且不再出现标准目录中的低级回退文件。
- 快速检查清单：确认标准目录只包含服务器真实返回的目标层级文件；检查 fallback 是否与标准缓存分离；目标层级请求失败后再
  生成回退；下载前统计不能把 fallback 算作已下载；更换缓存目录后核对任务的实际请求层级；不要用文件尺寸推断瓦片来源层级。

## FBX 预览同步贴图压缩和重复资源上传

- 现象：点击 FBX 预览后窗口长时间没有模型，进入页面后交互仍然卡顿；包含多张 4K PNG 的任务最明显。
- 影响范围：Assimp FBX 解析、Skia PNG 解码、CPU BC1/DXT1 压缩和 DX12 网格/贴图上传路径。
- 根因：点击事件先完整加载 Skia 软件预览，再完整加载 DX12 预览，同一批贴图被同步解码两遍；BC1 压缩也在 UI
  线程完成，页面只能在全部工作结束后打开。每张新贴图还与网格共用同一个 revision，导致已有网格、旧贴图和新贴图
  全量重传。线框索引按每个三角形写入三条边，共享边会重复绘制；DX12 失败时，软件回退会在高帧率下逐帧处理完整网格。
- 解决方案：点击后立即打开预览页。`std::jthread` 在后台解析 FBX，发布一次不可变 CPU 网格，再逐张解码 PNG 和压缩
  BC1；每张完成后进入结果队列并请求重绘。DX12 渲染线程每帧最多消费并上传一张贴图，网格缓冲只上传一次，已上传
  资源不因后续贴图完成而重建。切换任务、离开页面或析构时通过 `stop_token` 取消并 join。线框边使用标准化顶点对去重，
  默认模式改为纯贴图，避免刚进入页面就承担叠加线框成本。大网格不再预加载逐帧 CPU 绘制的软件回退。
- BC1 取舍：当前轻量编码器以“距块平均色最远的像素，再取距该像素最远的像素”近似颜色直径，把每个 4x4 块的端点
  搜索从全部像素对比较降为两次线性扫描。它保留 4 色插值和逐像素最近色选择，适合预览，不替代离线高质量纹理压缩。
- 验证方式：Release 下使用 19 MB、83977 顶点、165331 三角形、9 张 4096x4096 PNG 的真实任务测量，网格在
  111 ms 后可用；贴图依次在约 0.58、0.99、1.42、1.83、2.28、2.72、3.14、3.58、3.99 秒完成。总工作仍需约
  4.00 秒，但不再阻塞点击事件，并能逐张显示。`FbxPreviewRendererTest` 还覆盖立即返回、后台完成和取消后清理。
- 快速检查清单：确认文件 I/O、解码和 BC1 压缩不在 UI 线程；每张贴图完成只增加贴图驻留状态；一帧限制上传量；
  CPU 数据至少保留到对应 GPU copy 提交；取消后 worker 不再回调已析构对象；线框共享边只绘制一次；DX12 失败时不要让
  大网格无提示地退回高频 CPU 全量绘制。

## FBX DX12 首帧空白

- 现象：FBX 后台状态显示网格和贴图都已完成，但 DX12 预览窗口一直只有背景；日志中的命令提交并不代表已有像素。
- 根因：像素着色器在 `ps_5_0` 下声明 `Texture2D textures[1024]` 并用运行时索引访问，D3DCompiler 报
  `X3512 sampler array index must be a literal expression`，初始化因此提前退出。修复数组后，CPU 端矩阵仍把齐次
  `w` 保持为 0，且 CPU 的行主序填写与 HLSL 默认列主序不一致，顶点会被裁剪。最后，Skia 逻辑尺寸和 DPI 缩放下的
  实际 D3D12 back buffer 尺寸可能不同，使用前者设置视口会使模型偏移或被裁剪。
- 解决方案：像素着色器改为单个 `t0` 纹理槽，绘制每个批次时把对应纹理的 SRV（未就绪时为 null SRV）绑定到该槽；
  矩阵声明为 `row_major` 并显式设置 `m33 = 1`；视口、裁剪矩形和缩放统一使用 back buffer 的实际宽高。这样仍兼容
  Shader Model 5.0，并保留逐张贴图上传。
- 验证方式：使用 83977 顶点、165331 三角形、9 张 4096x4096 PNG 的真实 FBX，Release 宿主可见模型和卫星贴图，
  DX12 命令提交成功；核心 `FbxPreviewRendererTest`、`FbxTerrainTriangulatorTest` 和 `PostProcessFbxTest` 通过。
- 快速检查清单：DX12 空白时先读取 shader 编译错误；确认动态纹理访问没有依赖 `ps_5_0` 不支持的数组索引；检查矩阵的
  齐次 `w` 和行/列主序；最后从 `GrD3DTextureResourceInfo` 读取实际 back buffer 尺寸，而不是直接复用 Skia canvas 参数。

## FBX 旋转交互消息积压

- 现象：鼠标拖动旋转比滚轮缩放明显卡顿，模型本身已经在 GPU 上绘制。
- 根因：每个 `WM_MOUSEMOVE` 都向窗口消息队列投递一次重绘请求；鼠标事件频率高于渲染完成频率时，旧角度的重绘会排队，DX12
  三帧资源轮换又会在复用 command allocator 前等待 fence，最终表现为输入延迟和跳帧。滚轮事件频率低，因此不明显。这与卫星图
  拖拽曾遇到的问题同类：不能让高频鼠标消息堆普通 redraw，而要节流并尽快消费最新状态。
- 解决方案：FBX 页面复用卫星图的思路，增加独立的即时重绘消息和 4ms 拖动节流，同一时间只保留一个待处理即时重绘。左键拖动
  围绕模型中心 orbit，右键/中键/Shift+左键平移，滚轮缩放。相机默认使用 `yaw=0、pitch=90°` 的沿 Y 轴俯视姿态，匹配 FBX
  地形的 X/Z 平面；矩阵按 Y 轴旋转，而不是误把 X/Y 当作地面平面。离开页面时重置角度、平移和缩放，避免上次拖动状态影响下一次预览。
  旋转基准速度从 0.008 降为 0.004 弧度/像素，并在右下角提供旋转、缩放、平移速度滑块；用户调整结束后写入
  `cache/fbx-preview-settings.json`。
- 验证方式：Debug/Release `DomDownToolPreview` 构建通过，`FbxPreviewRendererTest` 和 `FbxTerrainTriangulatorTest` 通过；真实
  FBX DX12 预览已确认模型和贴图可见。

## FBX 低角度预览透视畸变

- 现象：FBX 地形低角度观看时，用户看到远处模型变大、近处模型变小，且相机无法贴近地面观察。
- 根因：DX12 顶点阶段使用的是手写仿射 clip-space 变换，齐次 `w` 固定为 1，并不是真实相机的 view-projection。
  这种矩阵在俯视时问题不明显，但低角度时不会产生正确的 `w=viewZ` 透视除法，深度和屏幕尺寸关系会显得反常。
- 解决方案：FBX 主预览改为 orbit 相机的标准透视 view-projection：X/Z 为地面、Y 为高度，`pitch` 可降低到接近水平视角，
  投影矩阵输出真实 `w=viewZ`；滚轮缩放沿视线推进相机，最近距离交互语义为 0，但渲染矩阵内部保留极小安全距离，避免
  相机落在 near plane 或三角形内部。平移不再改 clip-space 偏移，而是在 X/Z 地面平面移动相机目标点，贴近地面时不会
  因修改投影项导致画面被拉伸；Q/E 沿世界 Y 轴上下移动目标点，Q 为下降、E 为上升，复用中键平移的像素到世界单位换算
  和“平移速度”滑块。
  长按 Q/E 不依赖 Windows 键盘 repeat，而是按键只维护垂直方向状态，FBX 键盘帧调度器按 elapsed time 推进高度平移。
  帧调度器接入即时重绘路径，但保留最小帧间隔，避免无节流自循环把 UI 消息泵打满。速度面板增加“归零”按钮，用于
  恢复初始俯视角、平移和缩放。
- 快速检查清单：低角度透视异常时先检查顶点着色器输出的 `SV_POSITION.w` 是否来自相机空间深度；不要用固定 `w=1` 的
  仿射矩阵模拟地形透视；贴地观看需要同时放宽 pitch 下限、给真实透视保留非零安全距离，并保证 near/far 平面覆盖标准化后的模型范围。

## FBX Q/E 连续平移帧率低于鼠标旋转

- 现象：鼠标旋转已经流畅，但长按 Q/E 上下平移的帧率仍低一档，视觉上和鼠标拖动不一致；主观观察难以判断是帧率低还是
  移动速度/方向造成的错觉。
- 根因：鼠标旋转使用 FBX 专用即时重绘消息，最多保留一个待处理 redraw，并尽快消费最新相机状态；Q/E 虽然不再依赖键盘
  repeat，但仍由 `WM_TIMER` 以 16ms 间隔驱动。Win32 窗口定时器是低优先级消息，绘制较重或消息队列繁忙时会被合并/延后，
  实际节奏天然比鼠标即时 redraw pump 更松。
- 解决方案：Q/E 不再把 16ms 窗口定时器当作移动时钟。按键按下/松开只设置垂直方向；`scheduleFbxKeyboardPanFrame`
  负责安排下一帧。需要立即绘制时投递 FBX 即时重绘消息；如果上一帧刚结束，则用短的一次性窗口定时器补齐最小帧间隔。
  每帧绘制前按 elapsed time 调用 `verticalPanBy`，因此帧率提升不会改变平移速度。FBX 页脚显示最近约 0.5 秒的实测 FPS，
  用于区分真实帧率下降和操作速度错觉。
- 验证方式：`PreviewSearchUiTest` 增加静态检查，确认 Q/E 连续平移使用 `scheduleFbxKeyboardPanFrame`，且不再保留旧的
  `kPreviewFbxVerticalPanTimerId`。Debug/Release `DomDownToolPreview` 构建可验证链接和消息路径。
- 快速检查清单：键盘连续交互不要依赖键盘 repeat；不要让即时重绘自循环无节流运行；移动量按 elapsed time 计算，避免
  帧率变化导致速度变化；同一时刻只保留一个待处理 redraw 或一个补帧 timer，避免重回消息积压问题。

## FBX Q/E 即时重绘自循环导致无响应

- 现象：把 Q/E 从 16ms 定时器切到即时重绘消息后，长按按键会让预览窗口卡到无响应；鼠标旋转仍正常。
- 根因：鼠标旋转只在 `WM_MOUSEMOVE` 到达时请求重绘，并带有拖动节流；上一版 Q/E 在每次即时重绘完成后，只要方向非零就
  立即再次投递即时重绘，形成无帧间隔的自循环。DX12 绘制较重时，这会持续占满 UI 线程和 GPU 提交路径，KeyUp、窗口消息和
  普通 UI 事件都要排队等待，看起来就是无响应。
- 解决方案：恢复用户期望的“方向状态 + tick”模型。`WM_KEYDOWN/WM_KEYUP` 只把方向设置为上、下或 0；独立的
  `scheduleFbxKeyboardPanFrame` 负责 tick 节奏，并保证至少 4ms 帧间隔。即时重绘只负责执行一帧，不能自己无限贴着
  消息泵重入；需要补下一帧时必须经过帧调度器。
- 验证方式：静态检查确认存在 `scheduleFbxKeyboardPanFrame` 和帧间隔常量；Debug/Release 构建验证消息路径能编译链接。
- 快速检查清单：持续键盘输入必须是状态驱动，不应靠按键 repeat；tick 必须有明确帧率上限；绘制完成后若要继续下一帧，
  必须回到调度器，而不是直接无条件 post 自己。

## FBX FPS 显示停住和缩放帧率偏低

- 现象：FBX 页脚增加 FPS 后，空闲时 FPS 数字不再变化；滚轮缩放时显示帧率明显低于鼠标旋转。Q/E 和旋转显示 FPS 接近，
  但体感仍可能不同。
- 根因：FBX 预览最初是事件驱动渲染，只有加载、鼠标移动、滚轮、按键调度等事件触发 redraw。空闲时没有新帧，FPS 自然停在
  上一次采样值；滚轮缩放通常只产生离散 wheel 消息，采样窗口内 draw 次数少，因此显示为低 FPS。这不一定代表 DX12 draw
  本身慢，而是没有连续渲染心跳。
- 解决方案：进入 FBX 预览页后启动独立的 `kPreviewFbxFrameTimerId` 渲染心跳，约 16ms 触发一次 FBX 即时 redraw；离开 FBX
  页或窗口销毁时停止。相机输入仍只修改状态，不负责维持空闲刷新。FPS 显示由真实 draw 次数统计，因此空闲、缩放、旋转、Q/E
  都可以用同一把尺子比较。
- 验证方式：`PreviewSearchUiTest` 静态检查 FPS DOM、`startFbxPreviewFrameLoop` 和 `kPreviewFbxFrameTimerId`；Debug/Release
  `DomDownToolPreview` 构建验证 Win32 timer 和资源编译路径。
- 快速检查清单：性能显示必须先确认是否存在连续帧源；滚轮、按键 repeat 和鼠标 move 都是输入事件频率，不等于渲染帧率；
  需要比较交互流畅度时，用同一个 frame loop 采样真实 draw 次数，再判断是否是相机运动速度或 draw 成本问题。

## FBX TIN 细化批次过小导致导出末段长时间无磁盘写入

- 现象：117 张 FBX 贴图全部生成后，任务进度停在“生成 FBX 贴图 117/117”较长时间，期间几乎没有
  新文件写入，最终任务仍能成功完成。用户样例为 z16、30 米高程采样、KML 范围和 117 张 4096
  贴图，`plane.fbx` 最终约 145 MB。
- 排查路径：使用用户任务的同一瓦片缓存、DEM 缓存、KML 范围和导出参数构造本地基准，并分别计时
  高程准备、高度场采样、四叉树简化、TIN 网格构建、法线计算和 Assimp 写盘。不要根据“硬盘没有
  写入”直接判断死锁，也不要先把采样段数向上取整当成瓶颈。
- 根因：117 个贴图块会分别调用 `BuildFbxTerrainTin()`。旧实现每轮只加入 16 个超出误差阈值的
  候选点，随后从头重建约束 Delaunay 三角网、重新扫描全部候选点并排序。单块约 5500 个顶点时
  可能重复数百轮，重复三角化和误差扫描远高于 DEM 采样及文件序列化成本。
- 实测证据：优化前同一任务的高度场采样与四叉树简化为 2.55 秒，TIN 网格构建为 1121.84 秒，
  Assimp 写盘为 0.87 秒，总流程为 1154.69 秒。说明 327 段向 512 段取整会增加采样量，但不是
  本次主要瓶颈。
- 解决方案：保持误差排序、每轮重新验证和三角形总量上限不变，把单轮细化上限从 16 提高到 256。
